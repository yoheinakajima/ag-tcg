# Replit Scheduled Deployment Runbook — Standing Tournament Engine

> **Internal diagnostics only. NOT a Kaggle leaderboard.** This deployment runs an
> internal self-play tournament to rank candidate decks for operator insight. It
> performs **NO Kaggle upload, NO submit, NO auto-submit, and generates NO new
> candidates.** Internal standings are not predictive of Kaggle placement and are
> never a promotion or upload signal.

This is the operator runbook for running, monitoring, and recovering the Pass 36
tournament engine as a Replit **Scheduled Deployment** backed by **persistent
object storage** (the Pass 37 wrapper). It is the single page an operator needs to
keep the soak running safely.

---

## 1. What this is (and is not)

- **Is:** a bounded, cron-like job. Each run ("tick") pulls the persistent state,
  plays a small bounded number of internal self-play games, rebuilds projections,
  reconciles against storage, pushes a sha-verified snapshot, and releases its
  lease. The engine itself is the **unchanged** Pass 36 engine.
- **Is NOT:** an always-on web server, and **NOT** the root `Start application`
  workflow. That workflow wraps the frozen Kaggle entrypoint (`main.py`) and is
  **expected to stay not-started** — never start it to drive the tournament.
- **Source of truth:** persistent storage (Replit App / Object Storage). The
  local `data/tournament/` directory is a **disposable per-run working dir**.

## 2. Deployment configuration (exact)

The `.replit` `[deployment]` block is already configured:

```
deploymentTarget = "scheduled"
run   = python scripts/tournament_deployment_tick.py --max-games 20 --max-seconds 900 --storage-backend replit_app_storage --production
build = python -m pip install --user --break-system-packages replit-object-storage pyyaml kaggle-environments==1.30.1
```

- **`[tool.uv] package = false`** in `pyproject.toml` is REQUIRED — it stops the
  deploy build's automatic `uv sync` from editable-installing the root package
  into the read-only Nix store (the original Pass 37 build failure). The worker
  puts `src/` on `sys.path` itself, so no install is needed.
- The build uses `pip install --user --break-system-packages` because the Nix
  python is externally managed and uv targets the read-only store; `--user`
  lands deps in the writable `.pythonlibs` (PYTHONUSERBASE).
- `kaggle-environments==1.30.1` is pinned because the game engine is its
  **bundled `cabt` env** (`make("cabt")`); a different release could drop/alter it.

Regenerate this guidance anytime with
`python scripts/print_replit_scheduled_deployment_config.py`.

## 3. Concurrency invariant

Object Storage has no atomic compare-and-set, so the lease is best-effort plus a
local `flock`. Keep this ordering true at all times:

```
schedule interval (2h) > lease TTL (30 min) > job timeout (~25 min) > --max-seconds (15 min)
```

A cabt game takes ≈ 11–15s, so `--max-games 20` finishes well inside
`--max-seconds 900`. **Schedule:** `0 */2 * * *` UTC; **job timeout:** ~25 min.

## 4. Safety guardrails (must always hold)

- root `main.py` / `deck.csv` byte-identical to `data/baselines/v1_kaggle_349_8/`,
- `auto_submit` is `false` and refused if forced (config or `TOURNAMENT_AUTO_SUBMIT`),
- every event carries `no_upload=true`; **no** `SubmissionUploaded` /
  `KaggleScoreUpdated` events ever exist,
- never-schedule decks (retired / quarantined / **special_pilot_only** (Toxic,
  Durant) / invalid) are never scheduled; the held probe is retained,
- no new candidates are generated by the soak,
- production **fails CLOSED** (raises) if persistent storage is unavailable.

## 5. How to publish

1. Open the Publishing (Deployments) tool in this Repl.
2. Deployment type = **Scheduled Deployment** (not Autoscale / Reserved VM / Static).
3. Schedule = every 2 hours (`0 */2 * * *`), UTC.
4. Job timeout ≈ 25 minutes (below the 30-min lease TTL).
5. Confirm the run/build commands match section 2 (they come from `.replit`).
6. Publish. A successful publish means the run command exits 0 — see section 8 on
   why that is decoupled from game progress.

## 6. How to monitor

- **Health check (primary):** run the read-only checker against production:
  ```
  python scripts/check_tournament_health.py --mode prod \
      --out-json data/experiments/pass38_tournament_health.json \
      --out-md   data/experiments/pass38_tournament_health.md
  ```
  Exit code `0` = healthy (no hard failures); non-zero = a hard safety invariant
  failed — investigate before the next tick. Use `--mode local` to audit the
  working dir. Warnings (tiny sample size, low game counts) do **not** fail.
- **State snapshot:** `python scripts/build_pass38_remote_state_snapshot.py`
  pulls a read-only summary of the live ledger (counts, sidecars, runs, hash).
- **Deployment logs:** check the Publishing tool's logs for each scheduled run.
- **Scheduled vs manual:** `python scripts/build_pass38_scheduled_run_detection.py`
  classifies recorded ticks (the scheduled signature is `--max-games 20
  --max-seconds 900`).

## 7. Routine operations

- **Controlled manual tick (only if no lease is held):**
  ```
  python scripts/tournament_deployment_tick.py --max-games 3 --max-seconds 240 \
      --storage-backend replit_app_storage --production
  ```
- **Rebuild projections from the ledger (idempotent, no games):**
  `python scripts/build_tournament_projections.py`
- **Dry run / no games:** add `--dry-run` or `--no-games` to the worker to
  exercise pull/push without playing.

## 8. Troubleshooting

| Symptom | Likely cause | Action |
|---|---|---|
| Build fails with EACCES / read-only store | `uv sync` editable-installing root | confirm `[tool.uv] package = false`; do not add dependency-groups |
| Publish OK but zero game progress | missing `kaggle-environments` in build | ensure `kaggle-environments==1.30.1` in the build command |
| Worker exits 3 (storage_unavailable) | persistent storage unreachable | this is fail-closed; fix storage, do not run non-prod fallback |
| Worker exits 4 (lease_held) | another tick is running | wait for the lease (TTL 30 min) to expire/release |
| Worker exits 5 (conflict) | divergent `GameFinished` sha | inspect the ledger; never overwrite remote — reconcile |
| Games recorded `timeout`/`error` | per-game subprocess crash/timeout | expected to be tolerated; a failing game never fails the tick |

**Publish-success ≠ game-success:** a failing game is recorded `timeout`/`error`
and the tick continues; the worker exits non-zero only on a top-level/storage/
refused/conflict/lease error. When debugging a publish failure, separate "does
the run exit 0" from "do games make progress".

## 9. Incident reference — Pass 37 deployment build failure

The first publish failed because the deploy build's automatic `uv sync`
editable-installed the root project and tried to write `__editable__*.pth` into
the **read-only Nix store** (EACCES). Durable fixes: `[tool.uv] package = false`;
deploy deps via `pip install --user --break-system-packages`; pin
`kaggle-environments==1.30.1` for the bundled cabt env. Full detail in the Pass 38
addendum inside `docs/PERSISTENT_TOURNAMENT_DAEMON.md` and the report
`data/reports/pass38_scheduled_deployment_ops_report.md`.

## 10. Reset / recovery (only if explicitly needed)

The persistent ledger is the source of truth and is append-only; prefer
reconciliation over reset. If a reset is unavoidable, remove the derived state
(`events.jsonl`, `games/`, `projections/`, `runs/`, `storage_manifest.json`) from
**storage** and rebuild with `seed_tournament_pool.py` +
`build_tournament_projections.py`. **Never** delete tarballs and **never** touch
root `main.py` / `deck.csv`.

## 11. What "healthy" means

A healthy deployment shows: health checker exit 0 in both modes; the deployment
publishes successfully; no forbidden upload/submit events; every finished game has
a durable sidecar; manifest shas match the ledger; the scheduler worklist is
deterministic, excludes finished games, and never schedules a never-schedule deck;
the held probe is retained. Sample-size warnings are normal early in a soak and
clear as games accumulate.

Manifest sha integrity is a HARD check in `--mode prod` (the authoritative Object
Storage snapshot must be byte-consistent) but only a WARNING in `--mode local`: the
local working dir is disposable and may be rebuilt ahead of the last push (projections
carry a fresh `generated_at`), so a local sha drift just means "re-pull to reconcile,"
not corruption.
